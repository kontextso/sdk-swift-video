# Changelog

## Unreleased

First release of the Kontext Video SDK for iOS, v1 of the *Video Ads API & SDK v2* contract.

* Depends on KontextKit 0.3.0's `KontextKit` product only: the shared device, privacy and StoreKit providers, without the Open Measurement xcframework (the SDK does not measure with OMID yet).
* `KontextVideo.shared.initialize(with:)` (fire-and-forget, `async`, or with a completion), `user` (id, email or its hash, keywords; no demographics, OpenRTB 2.6 deprecated `yob` and `gender`), `regulatory` and `variantId` set later from anywhere; the next request carries them, ads already loaded or fetched stay.
* `VideoAds(content:)` per video; creating it sends nothing. The SDK assumes a full-screen player: every request carries the screen in its current orientation, and `show(in:)` fits the ad into the real view. The SDK reads the content playhead through `trackPlayhead(of: AVPlayer)` or `playheadProvider` when it needs one (the request's `player.playhead`, the `[CONTENTPLAYHEAD]` macro). No player protocol, nothing to start.
* `try await ads.format(.pause)` returns the format's `VideoAd.Bid` (price, size, duration, ...; nothing rendered). Every call asks for all formats with the `VideoAds`'s `sessionId` and the ids of the unshown bids it holds (`held`); the server re-serves those unchanged until they expire, so the same `Bid` and its loaded ad come back, and bids of other formats wait for their own call. The SDK follows the response: a new id or a no-fill drops the held bid (`.invalidated(.expired)`); an id it already used is ignored. Calls made while a request runs share it (`async let` for several formats); a failed request returns the held bid while it is valid. At most one unshown bid per format. No options, no automatic requests, no refetch.
* `bid.load()` renders the creative and returns a `VideoAd` ready to show; concurrent calls share one load, a later call returns the same ad. The page reports ready only when the creative can display at once. Loading fires nothing billable (only VAST `loaded`). `bid.reject()` / `ad.reject()` (`.notUsed`, `.outbid(winningPrice:)`) until `show`: the `notUsed` beacon with `[REASON]` and `[WINNINGPRICE]`, the WebView released; throws `.alreadyShown` after `show`. Expiry is lazy: found out at the next call, which throws `.invalidated(.expired)`; no timer, no notice (the server knows `expires`). Cancelling a caller stops only its waiting (`CancellationError`); the request or load continues.
* `destroy()` (or releasing the `VideoAds`, best effort) sends `notUsed` (`destroyed`) for every held bid, ends the ad on screen with `didEnd(.destroyed)` and fails what is in flight with `.destroyed`. A kill switch in an `/ads` response turns the whole SDK off: held bids are dropped with no notices, loaded ads cannot be shown (`.disabled`), the ad on screen finishes normally.
* `VideoAd.show(in:)` for overlay and pause ads inside the view the content plays in (an ad with several `sizes` gets the best fit for the view at show: the largest that fits unscaled, else the best scale still ≥ 50 %; `ad.size` is the chosen one), `show()` / `show(from:)` for full-screen linear ads (the presenter found on the key window, or named; `.presenterUnavailable` when none can present), `dismiss()` for the non-linear formats (`.wrongPresentation` on a linear ad, as `show(in:)` on a linear ad and `show()` on the others); at most one ad on screen in the whole app (`.anotherAdShowing`); `.containerTooSmall` leaves the ad ready; an overlay is removed by the SDK when its `duration` of time on screen elapses (`didEnd(.completed)`; the clock freezes in the background), `OverlayOptions.maxDuration` caps it at request time; `VideoAdDelegate` with the on-screen moments only (no `didInvalidate`: nothing is delivered before `show`), exactly one `didEnd(reason:)` per successful show and no "did show" callback (`show` returning is the signal); `didEnd`'s reason is the gesture (the ✕ is `.closed` in every format, a linear ad's Skip `.skipped`, ended by itself `.completed`) and `ad.isCompleted` says whether the creative ran to its end.
* Creatives: `image`, `video`, and `html` (third-party markup the frame page inserts into a sandboxed iframe only on `ad.show`; the SDK treats it like an image: impression at `show`, 1 s viewability dwell). No MRAID API yet.
* Low Power Mode: the request carries `lowPowerMode` (the server sells the impression as click-to-play); a video ad whose autoplay WebKit refused shows Play and waits for the tap.
* Tracking: every VAST entry fired once by the SDK with the macros substituted, each fire with its own `fid` for server-side dedupe, the click-through carrying the click's `fid` too; `overlayViewDuration` carries the active time on screen (`[VIEWDURATION]`, ms); a page ending itself after `complete` (`ad.close`, reason `complete`) fires no `close`; viewability (`viewable` / `notViewable` / `viewUndetermined`); the Kontext Frame Protocol v2 with the page.
* App Tracking Transparency on request, IDFA only when authorized, consent read from the CMP's IAB keys; `/config` kill switch and retry; `/debug` reporting when the server asks.
* Privacy manifest (`PrivacyInfo.xcprivacy`).
* Tests: 268 Swift Testing cases in about 45 s, including the lifecycle races (shared request and load, cancellation, reject or show while a request runs, expiry during a load or a request, destroy in flight) and whole flows through a real `WKWebView`; CI on every push.
